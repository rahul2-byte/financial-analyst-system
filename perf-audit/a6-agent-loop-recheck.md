# a6: agent-loop re-check (current merged code)

Scope: one report run traced through `finai/session_runtime.py` -> `RoutingPolicy.decide` -> `AgentLoop._run` (`agent_loop/runtime.py`) -> `ToolBatch` -> synthesis (`model_streaming.py`, `openrouter_service.py`) -> `normalize_report` / `publish_report` -> repair -> `session.py` persistence -> `bridge/server.py` `run.finished`. News prefetch/pipeline is excluded (another agent owns it).
Method: code reading plus small offline scripts (`PYTHONPATH=backend uv run --no-sync`; scripts in the session scratchpad: `q.py`, `b.py`). "Measured" = run here offline; "reasoned" = derived from code plus the a4/a5 numbers (a4: GLM via Hive, 149 runs; a5: reasoning split). No network, no model calls, no edits.

## Verdict

Nothing in the loop adds a sleep, a polling interval or a fixed wait on the happy path. Event-loop blocking and persistence are negligible (measured, below). What still adds real time is in three places:
1. the fast path is skipped for every report after the first in a session (F1);
2. a post-prefetch model round that is allowed to ask for more tools, which costs a whole extra model round plus a Jev checkpoint (F2);
3. slow-path behaviour: 30 s tool timeouts, a 12 s wrap-up grace that cannot fit a synthesis, and the 20 s per-line stream timeout (F4-F6).
The single biggest cost (default reasoning on the synthesis call, about 17 s of about 31 s, a5) is untouched and is the only one that can change content (F3).

## Ranked findings

### F1. Fast path is disabled for every report after the first one in a session (HIGH, measured by script)
- `runtime.py:1663-1687` (`_fast_path_applies`): requires `not completed_tool_ids` and "no assistant message with tool_calls anywhere in `history`". `history` is the whole persisted session: `session.py` `persist_message` appends every assistant tool-call message and every tool result (`runtime.py:~764` writes the prefetch assistant turn, `:1270-1330` the tool results). `completed_tool_ids` (`runtime.py:~362`) is computed from the same history.
- Measured: `_fast_path_applies` returns True for a fresh single-turn history and False when the history holds one earlier prefetched report (`b.py`: "turn1: True, turn2: False").
- What it costs: the second and later reports in the same session (and any report in a resumed session, or one after any lookup that used a tool) go back to the old path: a tool-selection model round (about 7.5 s median, a4/a5) plus the Jev checkpoint after tools (F2), plus any extra tool round. Reasoned: 7-10 s per such report; in an interactive terminal session this is every report except the first.
- Fix: evaluate the guard on the current turn only (messages after the last `user` message, and only the tool ids from that slice). Resume-after-approval keeps using the existing `approved`/`resumed_assistant` conditions.
- Required companion changes (otherwise the fix breaks):
  - `runtime.py:1693-1713` prefetch call ids are the constants `prefetch-1..N`. After the guard is relaxed they collide with the previous turn's identical ids already in `completed_tool_ids`, so `if call_id in completed_tool_ids: continue` (`runtime.py:1262`) would silently skip the new fetches. Make ids unique per run (include `factory.run_id` or a counter).
  - `successful_tool_signatures` is seeded from the whole history (`runtime.py:~370-382`). For a new turn on the same ticker, a repeated call then hits the duplicate branch (`runtime.py:1271-1301`) with `cached is None` (the per-run `tool_results_by_signature` is empty), so tools are disabled and the results are skipped. That leaves `evidence.facts` empty and gives an "evidence_unavailable" fallback or an extra round. Reasoned from code, not executed; verify with a two-turn test on the same ticker. Seed signatures only from the current turn, or treat a signature seen only in earlier turns as not-yet-done.
- Changes report content: no (same evidence, same prompt), apart from avoiding the stale-signature failure above. Risk: medium, needs the two-turn test.

### F2. After the prefetch, the synthesis round still has tools enabled, so the model can trigger an extra model round, a Jev checkpoint and more tools (HIGH when it happens; frequency reasoned)
- `runtime.py:1823-1840` (`_controller_tools`): with `controller_route is None` and no repair, it returns the full tool list. After the prefetch round `controller_route` is None (the checkpoint is skipped by `skip_checkpoint`, `runtime.py:1530`), so the synthesis call carries all tools. If the model asks for any (news is the usual one since `FINAI_REPORT_PREFETCH_NEWS=False`, `models.py:73`; also `run_technical_scan`), the run does: model round that emits only a tool call -> tools -> the advisory Jev checkpoint (`runtime.py:1523-1560`, not skipped this time, 10 s timeout x 2 attempts, `jev_service.py:96-97`) -> a second full synthesis.
- The extra tool-call round is tagged `purpose="synthesis"` because tool results already exist (`model_streaming.py:82-91`), so it gets `FINAI_REASONING_SYNTHESIS=unset` (default thinking on) rather than the cheaper tool-round setting. a5 puts a tool-selection call at 7.5 s with about 4 s of reasoning.
- Estimate (reasoned): per occurrence about 5-8 s model round + tool time (news about 13 s per a4, owned by the other agent) + checkpoint 0.5-10 s (20 s worst case if Jev times out and retries). If the model asks in 10-30% of reports (a4: extra tool rounds in 13/149 = 9% before the fast path; the config comment says "a small share"), mean cost is about 2-7 s per report, 25-30 s on the affected runs. Not measurable offline.
- Fixes, cheapest first:
  - (a) For the report contract, once the prefetch has run set `tools_disabled = True` for the next round (or set `controller_route` to a GENERATE_TEXT route). The model then writes from the prefetched evidence plus the availability snapshot. This can change content only if the model would have fetched news or a scan the prefetch omitted; the other agent's "news always prefetched" removes that gap, so pair (a) with it.
  - (b) Independently: skip the advisory Jev checkpoint for `answer_contract == "report"` whenever `evidence.facts` is non-empty (it is advisory and fails open at `runtime.py:1562`). Saves 0.5-10 s on any non-prefetch tool round.
  - (c) Give a "tool-call-only" round the tool-round reasoning setting (`purpose` should be "tool_selection" when `tools` is non-empty, regardless of tool results, unless it is the first synthesis). Saves about 3-4 s per such round.
- Changes report content: (a) possibly, see above; (b), (c) no. Risk: low-medium.

### F3. Reasoning on the synthesis call (about 17 s of about 31 s median), unchanged (HIGH, content-affecting, already in a5 item 1)
- `models.py:44` `FINAI_REASONING_SYNTHESIS = "unset"` sends nothing, so the provider default (thinking on for GLM, Haiku-class) applies. a5 measured about 923 reasoning tokens at about 54 tok/s = about 17 s (GLM). Not re-measured here. The per-purpose plumbing at `openrouter_service.py:336-339, 934-941` is in place; only the A/B and the default are missing.
- Fix: A/B `low` or `tokens:N` on about 20 prompts (grounding pass rate, repair rate, terminal status) and then flip the default. May change report content; risk medium (a higher repair rate gives time back, about 12 s per repair).

### F4. Slow-path time: tool timeouts and "wait for the slowest" (MEDIUM tail, reasoned)
- `tool_execution.py:21, 41` default tool timeout 30 s; the fast path waits for every prefetched call before synthesis (`runtime.py:1218-1232` awaits each result in order; the calls run concurrently, so the wait is the maximum). Typical tools are about 110 ms (a4, probably cached), so 30 s is 100-300x the median. Provider-internal limits stack inside it: `UPSTOX_TIMEOUT=20`, `YFINANCE_INFO_TIMEOUT_SECONDS=15` (`models.py:80, 102`), so an Upstox stall followed by the yfinance fallback (20 + 15 = 35 s) always exceeds the 30 s tool timeout. The tool then fails with `tool_timeout` after the full 30 s and returns nothing, so the whole wait is wasted.
- Fix: per-tool deadline of 12-15 s for the prefetch set (`_TOOL_TIMEOUT_OVERRIDES`), and align provider timeouts so the fallback fits (Upstox 5-8 s). Optionally, once `fetch_stock_data` and `fetch_fundamentals` are both done, give the remaining prefetch calls only a short grace (about 3 s) and proceed, recording them as unavailable via the existing availability path. Saves 15-25 s on affected runs, 0 at the median. Content: only on runs where data was slow (the report states the missing source). Risk: low-medium (more "limited evidence" reports under a flaky provider).
- Related (a2 data layer, noted only): every lane calls `upstox_fetcher.resolve_instrument(symbol)` first (`tool_runner.py:519, 631, 1017`); the cache is keyed by symbol, and two lanes start together, so both miss. Seeding the cache from the session-level resolution (`session_runtime.py:334`, which searched by query text, a different key) or resolving once before the batch removes one Upstox round trip per lane, about 0.3-1 s reasoned.

### F5. Budget/wrap-up logic can throw away a nearly finished synthesis and then run a second call that cannot finish (MEDIUM tail, reasoned)
- `runtime.py:497-514, 596-601, 625-630`; `models.py:61`; `runtime.py:187`: `max_run_seconds=150`, `wrapup_grace_seconds=12`. The synthesis call's deadline is `started + 150`. If it is cut off at 150 s (a4 p90 is 92 s; 5 of 149 runs had provider failures near 98 s+), `ModelBudgetExceeded` discards the in-flight output, the loop top starts a wrap-up round with only 12 s of grace and tools disabled. A report synthesis is about 30 s median, so the wrap-up cannot complete and raises `ModelBudgetExceeded` again, ending in `RunFailed` or the evidence-summary fallback. Net: up to 150 s of wall-clock for a failure, plus 12 s.
- Also: a repair is allowed to start at any time below 150 s (`runtime.py:1040-1044` `can_retry`), e.g. at 140 s with a 120 s repair timeout, but the deadline passed to the model is still 150 s (or 162 s in wrap-up), so it is cut off after about 10 s and then triggers another wrap-up round.
- Fix: (a) make the wrap-up grace for the report contract at least the observed synthesis p90 (about 45-60 s) or make the wrap-up a deterministic evidence summary (`_evidence_summary`, `report_validation_fallback`) with no model call; (b) require `remaining >= min_repair_seconds` (e.g. 30 s) in `can_retry`. Tail only; 0 at median. Content: only affects runs that already failed or degraded. Risk: low.

### F6. Stream silence limit is 20 s, not the configured 60 s (MEDIUM tail, reasoned)
- `openrouter_service.py:165` `OpenRouterRetryPolicy.read_timeout_seconds = 20.0`, never overridden (`:233-238` builds the policy without it), and used at `:530-534` (`asyncio.wait_for(lines.__anext__(), timeout=read_timeout_seconds)`). `OPENROUTER_READ_TIMEOUT=60` only configures httpx. a5 states a stalled stream burns "up to 60 s"; in the code it is 20 s per SSE line.
- Effect: a gap over 20 s between lines before the first byte makes a retry (restart of the whole call, backoff up to 0.5 s, `OPENROUTER_BACKOFF_BASE`); after the first byte it becomes a transport failure with partial output, which for a report turns into a parse failure and a full repair regeneration (about 12 s on gpt per a5, up to 120 s timeout). The a5 data show reasoning arrives first and streams, so this mostly triggers on provider stalls, not normal runs. Direction of the fix is ambiguous: raise to 45-60 s to avoid false failures on slow reasoning, or lower the connect/first-byte limit for tool rounds. Decide from `provider.retrying` counts. Content: no. Risk: low.

### F7. Fast-path conditions are narrow for natural report phrasings (MEDIUM, measured)
Tested with the real `resolve_instrument`, `wants_report`, `RoutingPolicy.decide` (`q.py`, with a tool set containing the fast-path tools, no Jev, no network). Hit = `deterministic_report_route`:
- Hit: "Analyze RELIANCE.NS", "analyse TCS.NS for me", "Report on TCS.NS", "I want you to analyze TCS.NS", "give me a research report on TCS.NS", "Write an investment thesis for HDFCBANK.NS", "Do a detailed analysis of ITC.NS", "stock report for SBIN.NS", "Could you analyze TCS.NS and write a report", "analyze the stock RELIANCE.NS".
- Miss because `wants_report` is false (`report_intent.py:10-24`: only the verbs analyze/analyse/research/compare at the start, after a short filler list, or the four marker phrases): "fundamental and technical analysis of TCS.NS", "Do a deep dive on INFY.NS", "Is INFY.NS a good buy?", "What's the outlook for RELIANCE.NS", "TCS.NS valuation", "How is ITC.NS doing", "Should I buy TCS.NS?". These become `model_answer`/freeform (no report contract, no fast path); a mode change, so not a pure perf issue.
- Miss for ordinary phrasing outside the filler list: "Please analyse HDFC Bank" (matched, because "please " is a filler; but the company name is unresolved offline, so no ticker). Not in the filler list: "Could you please", "kindly", "Hey,", "I need", "go ahead and analyze", "run an analysis". Reasoned from `_FILLER_PREFIXES`.
- Miss because the ticker is not resolved offline: "analyze Reliance", "Analyse TCS", "Give me a full report on Infosys", "research Tata Motors", "Create a stock report for Reliance Industries" (all `unresolved` with no Upstox fetcher, so Jev runs: 1-10 s). With a configured Upstox fetcher the session resolves these through a provider search first (`session_runtime.py:309-355`, up to 8 s timeout) and then takes the deterministic route; this is the common interactive case and I could not exercise it offline. Without a fetcher, bare uppercase symbols resolve through `_single_bare_symbol` but "TCS" alone in "Analyse TCS" did not (stopword/marker interplay in this offline run), so it falls back to Jev.
- Miss by design: comparisons ("Compare TCS.NS and INFY.NS") go to the Jev path (`routing_policy.py:~108-113`); and queries tripping the injection guard (`assess_input_safety`): "ignore any previous assumptions" (instruction_override) and "do not reveal your system prompt" (privilege_claim) flag as medium and skip the deterministic route; "act as an analyst" / "disregard older numbers" did not flag.
- Fix: widen `wants_report` carefully (add "deep dive", "analysis of", "full/complete/detailed report", "investment thesis", extra fillers) with tests; this changes the answer contract for those queries (freeform to report), so it is a product decision. Drop the `not safety.flags` gate when the flags are only medium and the query is otherwise a plain report ask, or accept the Jev call. Cost avoided per miss: the Jev route call (about 1-3 s typical, 10-20 s on timeout), and the tool-selection round if the fast path also becomes available (about 7.5 s).

### F8. Serial pre-loop steps (LOW-MEDIUM)
- `session_runtime.py:86-89` -> `:309-355`: instrument search (to_thread, 8 s timeout) is serial before routing and before any prefetch. It is a true dependency for company-name queries (the ticker is needed for every tool), so it cannot overlap with the prefetch; it can overlap with the LLM/HTTP prewarm (already started at `:83`). Typical cost reasoned 0.3-1 s; 8 s on a hung provider (`INSTRUMENT_SEARCH_TIMEOUT_SECONDS`, `:54`); a worker thread outlives the timeout but does not block the loop. Fix: lower to 3-4 s and fall through to the bare-symbol result. Explicit tickers (regex, no network) skip this entirely.
- The Jev route call (when the deterministic route does not apply) is serial after resolution and needs its result (`resolved_ticker` is in the context), so it cannot overlap with it. It could overlap with the start of an OHLCV prefetch for a resolved ticker (the prefetch is cheap and idempotent), saving the Jev latency (1-10 s) on report queries that miss F7 but have a resolved ticker. Needs a speculative-start design; only worth it if F7 stays narrow. Risk: wasted fetches if Jev denies/clarifies.

### F9. Things checked and found cheap (no action)
- Measured (scratchpad `b.py`, tmpfs-backed scratch dir, so real-disk fsync could add about 5-30 ms): `ReportDraft.model_json_schema()` + `json.dumps` per run 0.44 ms (`runtime.py:322`); `PromptRegistry.bundled()` 7 ms and `SkillRegistry.bundled()` 3.4 ms, only reached as fallbacks (`session_runtime.py:119, 253`; `runtime.py:~250`) because `resources.prompts`/`skills` are normally set; trace ledger appends for 151 events 2.5 ms total (`ledger.py:37-65`, fsync only at run boundaries in `session_store.py:19, 70`); `write_run` with 151 events 4.6 ms (`session_store.py:80-104`, runs in the `finally` of `session.py:~222`, before the bridge's `run.finished`, so it is on the critical path but about 5 ms); `ToolRunner.definitions()` (deepcopy + prompt lookups) is called many times per run (`runtime.py` `_allowed_tool_names`, `_controller_tools`, session routing) but is microseconds.
- Not measured, reasoned small: `build_report_view` (`bridge/server.py:327-352`, `report_view.py:128`) runs synchronously on the event loop after `run.completed` and before `run.finished`: dict/regex work over a few KB plus the OHLCV material; expected single-digit ms; it can only matter if `latest_ohlcv()` is large (1y daily is about 250 rows). `normalize_report` + `publish_report` are regex/JSON over about 6-10 KB, ms. `sanitize_untrusted_payload` + `assess_input_safety` per tool result (`runtime.py:1347-1350`) are CPU on the loop per tool, ms for the payloads here; worth a profile only if payloads reach tens of KB.
- Event-loop blocking: tools run through `asyncio.to_thread` (`tool_runner.py:308-310`), instrument search too (`session_runtime.py:334`), TechnicalEngine in a thread (`tool_runner.py:621, 700`). No `time.sleep` or `requests` calls in `finai/` or `app/core/agent_loop/`; the only `asyncio.sleep` calls are `sleep(0)` yields in `_emit_text` (`model_streaming.py:~245`) and `openrouter_service.py:591`, and the retry backoffs (`openrouter_service.py:493, 770`, max 4 s cap, random 0-0.5 s on the first retry; `jev_service.py:206`, at most 0.5 s). Retry backoff itself is not a cost (a5: 15-746 ms); the cost is the connect timeout (a5: ConnectTimeout x22 at 5 s; now `OPENROUTER_CONNECT_TIMEOUT=3.0` plus prewarm).
- Tool concurrency (`tool_batch.py`): two lanes (OHLCV: stock_data then technical_overview; fundamentals: fundamentals then fundamental_scan). The second call in each lane reuses the runner cache, so the serial hop is cheap; wall-clock is about max(lane A, lane B). Fine.
- Output review (`runtime.py:712-757`) is freeform only; not on the report path. Report repair calls are the only other optional model call; a repair is a full regeneration (max_tokens 8192, timeout 120 s), reasoning "low" (`models.py:43`).
- Repair triggers still reachable after `normalize_report` (`report_normalize.py` fixes only citation_source_id, claim_evidence_ref, fact_marker_id, numeric_ref_id, numeric_ref_link, numeric_value_link, plus JSON fences/trailing commas): `numeric_claim_unbound` (digits in prose with no `[[fact:ID]]`, `publication.py:252, 361`), `claim_unsupported`/`claim_citation_missing` (`:227-229, 330-334`), `numeric_fact_unverified`, `degraded_source_claim` (`:344`), `unsafe_guarantee_claim`, `major_claim_unsupported`, `duplicate_*`, `citation_source_url_missing`. Each costs one full regeneration (about 12 s on gpt-class per a5, GLM unmeasured). Biggest remaining candidate for a deterministic fix is `numeric_claim_unbound` (unbound bare numbers in prose), but "bind or drop" there edits claim text, so it is content-affecting and fail-closed concerns apply; leave unless the repair rate on the target model is measured (a5 item 6: persist usage/repair markers first).
